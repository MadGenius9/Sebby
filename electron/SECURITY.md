# Desktop privilege boundary — AI integration checkpoint

The renderer is an unprivileged interface. Preload exposes named intent-specific methods, not Node, Electron, a generic IPC sender, raw filesystem paths, a shell, credential readback, or arbitrary command execution. Main validates the exact sender window and main frame URL. Context isolation and Chromium sandboxing are enabled; Node integration, webviews, navigation, new windows, downloads and browser permission grants are denied. Production renderer requests cannot access the network or files outside canonical built-renderer assets.

## Explicit authority

- A native folder picker grants the selected workspace for this session only. No folder silently reopens.
- Source browsing uses an extension allowlist, 256 KiB per file, five directory levels, 300 results and 5,000 scanned entries. Hidden paths, dependency/output folders, secret-like filenames, absolute/traversal/drive/UNC paths and symlinks are rejected. This is **not secret detection**; ordinary source can contain secrets.
- Notes are create-only root .md/.txt files, with native approval and no overwrite.
- File edits use bounded complete-content previews, before/after hashes, backend rejection of truncated review, native approval, backups and target revalidation. Undo is separately approved and rejects post-edit changes. Undoing an unchanged newly created file explicitly deletes that file. There is no arbitrary delete/rename endpoint.
- Native selection can configure a trusted Git executable for this session. Each fixed read-only status command needs native confirmation. No executable path is accepted from renderer. Output/time bounds and cancellation exist. Running tasks are stopped on app quit.
- The service includes npm-test/npm-build plans, but no executable is configured for them and no UI exposes setup. Windows npm execution explicitly fails until process-tree containment is implemented. Npm scripts are arbitrary code, **not sandboxed**; future enablement must disclose script/lifecycle content, environment, network/credential exposure, budget, process cleanup and consent.
- Task completion/running transitions and assistant-message insertion are not exposed directly through preload. Approved deterministic utilities create their own immutable-kind tasks; arbitrary AI goals cannot be repurposed. Observed results stay awaiting-review until a separate native confirmation rechecks report identity/hash. Cancellation aborts scanning. Team roles/names, skill instructions and connector bookmarks never grant capabilities. Retiring a specialist does not erase task evidence.
- Connector registry itself makes no network requests and collects no credentials. Explicit native-approved MCP discovery is a separate main-process HTTPS exception: validated saved endpoint, all-public DNS answers, pinned TLS address/hostname, no proxies or redirects, bounded JSON and timeouts, no credentials, workspace data or tool invocation. Every attempt requires fresh consent; server text is untrusted and escaped. Real endpoint interoperability remains untested.
- Optional OpenAI, Anthropic and xAI adapters use separate fixed official HTTPS endpoints with verified TLS; no caller-supplied base URLs, proxies, redirects or automatic retries. They remain unconfigured until an explicit provider-specific existing credential and model are supplied. Presence is not authentication/model-access verification. Connection tests require separate native consent and may incur charges.
- Text chat discloses selected memory, skills, files, bounded history and output limits before native consent. Named AI specialists have bounded calls/context/output and only declared local read/reviewed-edit tools; no terminal, installation, credential, arbitrary network or connector tool. Additional file reads require outbound-data approval. A distinct provider coordinator result precedes separate user acceptance; neither model output nor renderer flags mark work complete. Main-owned full diff review precedes native file-write confirmation. Cancellation cannot undo already dispatched API charges or committed edits.
- Provider keys come from explicitly enabled provider-specific environment variables or OS-encrypted profile storage. The user-authorized masked key-entry field necessarily holds a new key transiently in renderer/IPC memory before encryption; no readback endpoint exposes saved or runtime keys. Entry is excluded from React state, localStorage, logs and backups and is promptly cleared, but JavaScript strings cannot be reliably zeroed. OS encryption availability is required; missing/basic_text storage fails closed with no plaintext fallback. Encrypted envelopes bind profile UUID and provider, so imported profile metadata cannot redirect another provider's stored key. Invalid/unavailable stored keys never silently fall back to environment keys. Native Windows encryption and UI behavior remain unverified.
- SSE streams, tool arguments, continuations and result sizes are bounded. Opaque encrypted reasoning remains in main-process memory only for continuation, never persisted or emitted to renderer. Refusals/incomplete streams do not grant tool execution or completion. Usage comes from provider-reported numeric counts; missing usage is not treated as zero and no currency cost is inferred.

## Data and recovery

Stores are versioned, bounded, validated, serialized and atomically replaced under userData. Personal and canonical-folder-hashed memory are separate. Other local collections are app-wide. Ordinary data, logs and edit originals are plaintext; the separate provider credential vault is OS-encrypted and excluded from exports. Do not store keys or passwords in chat, memory, skills or bookmarks.

Backup schema allowlists nine local stores (including nonsecret provider profiles and appearance) and rejects unknown fields/files, credential vaults and executable authority. Import validates in a staging directory; restore requires native confirmation and quiesced writers, retains recovery copies, uses rollback/journal recovery, then restarts. Single-instance lock prevents ordinary concurrent app writers. Restore maintenance rejects new IPC work. Exports validate each store but are not a cross-store atomic snapshot. Power-loss atomicity is not guaranteed.

## Limits

This is **not** a hardened sandbox against an adversarial local process modifying the workspace concurrently. Canonical paths, symlink rejection and content hashes reduce accidents but do not eliminate TOCTOU/hardlink/reparse-point attacks. Only use folders you control, not hostile shared/network locations. Windows handle-relative traversal/reparse protections and Job Object lifecycle handling still require native implementation/validation. File replacement preserves ordinary permission bits, not all platform ACLs/xattrs.

Main-process service/IPC tests and DOM component tests do not prove Electron runtime security, Windows file semantics, native dialogs, notification/voice behavior or installer trust. Actual Electron/Windows, live-provider and GPU verification remain unperformed in the current environment. No telemetry, crash uploading, signing or auto-updater is enabled. Optional silent notifications require session-only native consent, disclose lock-screen title visibility, and are marked delivered only after a native show event; all tests used fake native objects. Shutdown aborts producers and gives local store queues up to three seconds to drain; interrupted task recovery remains the fallback, not a guarantee against power loss.

Development is only `--dev` on an unpackaged app at fixed `http://127.0.0.1:5173/`; do not use an untrusted server on that port. Dev CSS permits inline styles solely for Vite; production CSP does not. Keep Electron and dependencies patched and repeat native release checks before distribution.
